# AutoClip quality and release requirements

Follow [docs/TESTING_SOP.md](docs/TESTING_SOP.md) for every test and release. [docs/TESTING_ACCEPTANCE.md](docs/TESTING_ACCEPTANCE.md) documents the acceptance tooling; where they differ, the SOP wins. Use [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) for release operations.

- Diagnose the latest report using its version, platform and build. Check production data (PostHog `studio_generation_finished`, Sentry by release) before and after a release. Preserve unrelated work, user data and secrets. Use isolated data directories for every test.
- For a production defect, reproduce the trigger and add a regression test that fails before the fix and passes afterward, runnable in CI.
- Run `python scripts/quality_gate.py --report /absolute/local/path/quality.json` before claiming a candidate passes source checks. Keep all eight UI locales consistent. Python correctness lint, frontend lint/types/tests/build and backend tests are blocking.
- Freeze the candidate before installed-package testing. At most two rebuilds per version; later findings go to the next version unless S1. Batch fixes before rebuilding. Results for modules untouched by `git diff` stay valid without re-testing or inheritance paperwork.
- Installed-package acceptance is the SOP golden path (G1–G7) on Windows x64 and macOS arm64 plus the change-impact items, within the SOP time boxes. Record one page per platform. Only S1 findings block; untested or unknown items are classified by the release owner and listed as Known Issues, not treated as automatic blockers.
- Do not invent extra process (private budget ledgers, UI leases, quota guards, supervision windows, new evidence contracts). If an environment blocks progress for 30 minutes, stop and hand it to the maintainer. Report progress every 30 minutes in three lines: done, blocked, next.
- Never promote with `gh release edit`, change an existing tag, claim a local fix is shipped, or close an issue before the fix is released. Hotfixes start from the affected tag with only the necessary repair and its regression test; bring fixes back to main.
- The maintainer authorizes each release once at the start: paid model budget (default ≤ ¥10), tag, Pre-release and promotion after the SOP observation. Contacting testers, halting a release and spending beyond the budget need separate authorization. Never upload raw PostHog/Sentry exports, credentials, personal paths or user media to the public repository.

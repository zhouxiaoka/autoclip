# AutoClip 业务需求到埋点的映射方案

日期：2026-09-29。状态：实施规格草案；事件名为目标契约提案，尚未实现或上线。

依据：[业务数据需求](ANALYTICS_BUSINESS_REQUIREMENTS_2026-09-29.md)。现状证据见[系统评审](ANALYTICS_SYSTEM_REVIEW_2026-09-29.md)。本稿只定义为满足需求应获取的事实，不以现有 SDK 能采什么决定产品目标。

## 1. 范围和准入规则

第一期闭环：可观测首次启动 → 真实素材制作 → 确认交付 → 再次制作。配套最小配置诊断、质量反馈和来源信息；社区和赞助经营数据先用独立台账。

任何新增事件必须说明：服务的指标、触发事实、记录方、统计对象、允许字段、去重规则和验收样例。没有这些说明，不增加埋点。

不把每个点击、组件曝光、接口调用都变成业务事件。现有诊断事件可以保留，但负责人看板只使用通过契约验收的事实。

## 2. 需求与证据对应

| 业务需求 | 指标/问题 | 必须获得的事实 | 获取方式 | 当前处理 |
|---|---|---|---|---|
| 首次得到价值 | 首次真实交付设备数、7 日激活 | 合格首次启动时间、素材用途、有效视频、确认交付、匿名设备 | 生命周期 + 制作结果 + 保存结果 | 改造生命周期与 Studio 关联；复用原生保存证据 |
| 持续价值 | 7/28 日再次出片 | 同设备、不同制作任务的真实交付 | 同一事实表推导 | 不新增“留存成功”事件 |
| 首次阻碍 | 哪一步失败、等待或无法观测 | 阶段进入、执行受理、终态、错误分类、重试、时间 | 操作层与后端执行摘要 | 统一阶段/尝试；修复快照误归因 |
| 配置门槛 | 保存配置后是否真正可用 | 配置类别、连接测试结果、实际执行采用的 Provider | 设置与执行摘要 | 复用保存/测试事件；禁止把保存当连通 |
| 质量 | 成片可用程度、主要问题 | 被邀请反馈、实际回复、受控质量选项 | 可跳过的抽样反馈 + 固定素材评测 | 新增最小结构化反馈；自由文本走独立反馈入口 |
| 增长来源 | 哪些渠道带来实际成功 | 来源类别、证据方式、活动标识、首次成功 | 受控来源记录 + 官网聚合 + 台账 | 来源不完整时保留未知；不强行跨站关联 |
| 版本改善 | 成功、耗时、影响范围变化 | 发布版本、系统、场景、执行结果 | 同一业务事实 + Sentry 诊断 | 统一维度，不再新增版本专属事件 |
| 社区与赞助 | 持续贡献、到账、投入、合作价值 | GitHub 记录、投入、合作报表、Provider 效果 | 平台聚合与私有台账 | 不放进应用埋点；复用赞助链接点击 |

## 3. 先统一统计对象

| 对象 | 含义 | 生命周期 |
|---|---|---|
| 匿名设备 | 当前应用存储中的随机统计标识，不是自然人 | 沿用已有匿名体系，不新增指纹 |
| `flow_id` | 一次明确的制作工作，从导入到成片交付 | 重试、修改、重导出沿用；新制作工作新建；仅本地映射内部项目 |
| `operation_id` | 一次用户发起的阶段操作，包含受理前失败 | 发起时生成，请求重传沿用；用户再次操作新建 |
| `attempt_id` | 后端受理的一次阶段执行 | 初筛、制作、渲染各自有 attempt；重试新建；与 operation/flow 关联 |
| `artifact_id` | 一份可交付视频产物 | 同一产物再次下载沿用；新版渲染产物新建 |
| `event_id` | 一条已经发生的事实 | 重复观察和传输沿用，不能每次轮询重建 |

一个 flow 可以有多个阶段、attempt 和成片。用户再次出片用不同 flow 判断；它是新的制作任务代理，不声称识别了不同视频内容。复制草稿、重试、重渲染默认仍属原 flow，避免制造虚假留存。

所有对外关联 ID 随机生成，不含路径、标题、原始项目 ID、媒体 hash 或可反推素材的信息。新增此类字段属于契约变化，需要同步白名单与隐私说明。

## 4. 目标事件目录

### 4.1 第一阶段必要事件

名称可以在实现时调整，但事实定义不得漂移。以下统一事件族将通过适配已有流程得到，不要求所有业务代码再加一套独立发送。

| 事件 | 准确触发时机 / 唯一记录方 | 主要专属字段 | 对应需求 |
|---|---|---|---|
| `app_session_started` | UI 可交互，生命周期模块每次运行一次 | `session_id`, `observation_start_kind` | 可观测启动、新设备 cohort |
| `workflow_operation_requested` | 用户已提交有效操作、即将调用服务；统一操作适配层 | `flow_id`, `operation_id`, `stage` | 操作量、阶段进入 |
| `workflow_operation_resolved` | 获得受理/拒绝结果，或客户端无法确定；统一操作适配层 | 同上，`result=accepted/rejected/transport_unknown`, 受理时 `attempt_id`，受控错误码、请求耗时 | 请求阻碍与后端执行分界 |
| `workflow_attempt_started` | 后端实际开始执行，执行摘要记录 | `flow_id`, `operation_id`, `attempt_id`, `stage`, 实际时间 | 排队/执行时间 |
| `workflow_attempt_finished` | 后端持久化该次执行的终态，执行摘要记录 | 同上，`outcome=completed/partial/failed/cancelled`, 受控错误码、目标计数、耗时 | 成功、失败、重试、部分成功 |
| `artifact_generated` | 视频落地且通过基本非空/可读检查，渲染结果记录 | `flow_id`, 渲染 `attempt_id`, `artifact_id`, `media_kind=video` | 成功生成，区分候选与实际成片 |
| `artifact_delivery_requested` | 用户请求获取指定成片，下载适配层记录 | `flow_id`, `artifact_id`, 下载 `operation_id`, `delivery_mode` | 交付意图 |
| `artifact_delivery_resolved` | 保存操作得到可确认结果，下载适配层记录 | 同上，`evidence=native_saved/bytes_received`, `outcome=completed/failed/cancelled`, 受控错误码 | 成功交付；不同证据单列 |

阶段 `stage` 第一版限定 `import/screen/produce/render`。转写等内部步骤先用于受控失败分类，确有决策需求后再细分，避免出现大量阶段事件。取消只记录明确的取消结果；网络异常不等于后台失败，客户端拿不到响应用 transport_unknown。

渲染完成与产物生成来自同一条本地结果证据，分别表达执行结果和产物对象；统计任务成功不能把两条事件累加。目标数、候选数和成片数分别定义。

浏览器原生链接下载只能发 delivery_requested；如实际读取了非空响应，可记录 bytes_received，但不算磁盘保存成功。没有结果证据时不虚构 resolved。超时未观察到由报表标为未知，不新增“猜测失败”的终态。

### 4.2 为具体决策补充的事件

| 事件/现有能力 | 要求 | 优先级 |
|---|---|---|
| 配置保存、Provider 测试 | 复用现有 api_key_configured/provider_test_finished/vision_provider 相关能力，统一到 `provider_configuration_saved`、`provider_connection_tested` 的目标语义；只允许 Provider 枚举、能力类别、结果、错误码；HTTP 成功不等于模型测试成功 | 首次阻碍分析同步完成 |
| `quality_feedback_prompted` | 提示实际展示时记录；受控抽样和频率限制；有随机 `prompt_id` 与 artifact 关联 | 最小质量反馈 |
| `quality_feedback_submitted` | 主动提交受控选项时记录；`prompt_id`、可用性四档、问题类别；重复提交按同一反馈的修订处理，不算多人回复 | 最小质量反馈 |
| `acquisition_source_recorded` | 第一次获得可信来源时记录；来源类别、受控活动代号、`evidence=campaign/self_report`；未知在报表保留 | 基础来源归因 |
| `use_case_reported` | 用户主动选择使用场景时记录；枚举场景、unknown/other，不把模型推测当自报 | 基础场景分析 |
| `sponsor_link_opened` | 保留现有受控赞助商/位置/目标字段，继续只表示点击 | 复用 |

结构化质量反馈属于主动提交：如匿名统计关闭但用户明确提交，依独立反馈规则接收，不附加设备或行为链路标识；提示曝光不绕过统计开关。此类反馈单独列来源，不能并入具备曝光分母的回复率。

## 5. 通用字段和采集边界

每条业务事件由一个公共入口构造不可被调用方覆盖的 envelope：

- 契约版本（暂定新契约 `business_schema_version=3`）、event_id、发生时间、观察时间。
- app_version、environment（production/development/validation）、runtime（desktop/web）、entrypoint（ui；CLI/MCP 后续单独设计）、os。
- flow 相关事件继承 `material_origin=user/sample/unknown`、`source_type=file/youtube/bilibili/other_url`；不能因字段缺失就默认为真实素材。
- `observation_start_kind=fresh_install/existing_install/unknown`：fresh 需要应用本地首次运行证据；升级到新统计版本不算新安装，无法确认时 unknown。
- 场景以用户自报为准；时长仅在分析等待/失败需要时采集粗区间。Provider 使用受控枚举，未识别自定义服务归 other，不上传 Base URL、任意模型字符串。

公共 envelope 与各事件字段都执行运行时白名单校验，拒绝任意对象展开。业务素材正文、路径、标题、Key、联系人不进入该链路。原始失败正文留在本地；上传受控分类。

本地执行记录不等于有权上报。只采集启用统计期间明确登记的工作；关闭时立即停止并清理待发分析记录/映射，保留必要业务数据。重新开启不扫描历史工作补传。独立反馈按其主动提交规则处理。

后端先提供本地持久化事实；对外发送仍通过受同意约束的适配层。不能直接默认开启后端全量发送来补齐数据。

## 6. 指标计算：尽量由事实推导

| 指标 | 计算规则 | 不新增什么 |
|---|---|---|
| 每周成功出片设备 | 在统计周发生至少一次 user 素材、有效视频、确认 native_saved 的设备去重；运行端/证据分列 | 不新增“活跃用户”事件 |
| 首次成功 | 同设备最早合格交付；区分完整历史与“新契约下首次观察” | 不用客户端布尔值直接声明终身首次 |
| 7 日激活 | 可确认 fresh_install cohort，在首次可交互启动后 7×24 小时内合格交付 / 已满窗口的可观测 cohort | 不用下载次数做分母 |
| 7/28 日再次出片 | 最早合格交付后窗口内不同 flow 的再次合格交付；仅成熟 cohort | 不新增“留存事件” |
| 一次成功与重试挽回 | 在 flow 内按 stage 的执行序列判断首次 attempt 与后续结果；按阶段报告 | 不把不同阶段当作重试 |
| 终态完整性 | 固定观察期限后，已受理 attempt 的已知终态、仍进行、未知三类分列；初始可用 24h，长任务另报 | 不用全体用户推算采集覆盖 |
| 首次交付耗时 | 合格启动到交付、导入请求到交付分别计算；负时差/明显时钟异常隔离 | 不把执行时长当全旅程耗时 |
| 质量反馈分布 | 按 prompt 去重的回复分布；曝光回复率仅同采集范围与抽样队列计算 | 不把未回复归为满意 |
| 来源效果 | 已记录来源下的合格首次成功；列明未知、自报、链接来源 | 不把活动期间增量全部归因给活动 |

cohort 为按同一起点形成的一组设备。历史数据不完整时，图名必须写“观察到的首次成功”；严格新用户激活只使用合格新设备队列。上线前后不能无标记拼接。

## 7. 现有埋点如何处理

| 当前事件/实现 | 决定 |
|---|---|
| app_installed/app_opened | 保留历史定义，新增契约用真实可交互启动及首次观察来源；不要把旧 app_installed 重解释成精确安装 |
| video_imported/clips_exported/processing_failed | 冻结为 legacy 历史信号；新指标排除，不删除旧数据 |
| 旧 operation requested/accepted/request_failed | 复用统一包装思路，加入业务阶段与明确传输未知；映射到目标事件族 |
| studio_* requested/accepted/finished | 复用业务挂点，补关联与不可变事实；逐步切换为统一契约，避免永久保留两套独立发送逻辑 |
| studio_download_saved/failed | 复用真实原生结果，加成片/任务关联与受控分类 |
| media_download_received | 保留“收到字节”的证据级别，不升级成“保存成功” |
| social_publish_* | 保留现有边界，首期不作为主激活终点；scheduled/inbox 不等于已发布 |
| pageview、草稿保存、复制、改写等 | 可留作诊断；没有决策需求时不继续增加曝光/点击粒度 |
| feedback_submitted | 保持独立主动反馈契约，不要求与匿名行为强制合并 |

迁移需有一张契约/版本矩阵与切换日期。验收对照优先在 validation 做；如需要生产双发，必须明确限期与新指标过滤条件。禁止将两套事件直接相加。

## 8. 交付顺序与验收

1. **冻结指标与事实字典。** 为每个指标写出一组可手算的样本；确认哪些一期只能显示未知。
2. **统一基础身份与结果证据。** 先修隐私门禁、阶段误归因；完成 flow/attempt/artifact 和本地终态摘要。
3. **接通一个真实桌面路径。** 从真实素材到保存，覆盖失败、重试、重复下载；再适配其他入口。浏览器保持其真实证据边界。
4. **生成负责人指标。** 激活/复用由上述事实推导，先校验完整性；新 cohort 等窗口成熟才显示最终率。
5. **补最小质量反馈、来源、场景。** 同步官网/社区/私有台账，使周报能指导实际行动。

### 必测业务样例

- 两个素材同时制作：A 失败、B 成功，不能串成 A 成功。
- 同一 flow 首次制作失败、重试成功：一次首次失败、一次挽回、一个成功 flow。
- 同一视频保存三次：三次交付操作、一个产物、一个成功设备，不算再次出片。
- 示例素材完成后真实素材失败：示例引导成功，真实激活未成功。
- API 超时但后台完成：请求结果未知，执行结果完成，不能记两次失败。
- 前端关闭后后台完成、重新打开：按原 attempt 恢复事实，不能伪造新任务或丢失阶段归属。
- 关闭统计后完成任务：不补报；重新开启不回放关闭期间记录。
- 安装旧版本后升级：新契约首次观察不计作新安装。
- 浏览器点击下载：仅意图，不计桌面保存成功。
- 两个目标一成一败且成功产物已保存：目标 partial 与一次成功交付并存，不互相覆盖。
- 未满 7/28 日窗口：显示观察中，不计入成熟转化分母。
- 只有 development/validation 收数：生产看板显示无数据，不显示业务成功率为零。

最终验收由负责人拿已知样本核对指标，而不止检查“PostHog 出现了新事件”。本次只产出规格，没有新增采集、修改线上看板或启用任何回传。

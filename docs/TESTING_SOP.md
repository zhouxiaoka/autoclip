# AutoClip 测试验收 SOP

> 这是发版时**实际执行**的手册。人和 agent 都按它干活，目标是在固定时间内，用固定的素材和步骤，给出明确的 GO / NO-GO。
> [TESTING_ACCEPTANCE.md](TESTING_ACCEPTANCE.md) 是验收工具（Internal / Release Acceptance）的参考说明，不是每次都要走完的流程。两者冲突时以本文为准。

## 0. 为什么要有这份 SOP

1.5.4 的验收持续了 3 天，最后正式记录只签了 Mac 2/10、Windows 0/10、回归 0/52，结果是由负责人豁免发版。资源主要浪费在下面几处，本文每条规则都针对其中一项：

| 浪费 | 实际发生 | 本文的对策 |
|---|---|---|
| 边测边修边重建 | 候选换了 8 次（5531b322 → … → 90edc851），每次重建，旧证据就作废 | §3 冻结规则：每个版本最多重建 2 次 |
| 造工具代替测试 | 为了复用旧证据，写了影响承接合同 v1/v2（PR #288、#291） | §5 证据只要一页清单；产品代码没变，旧结果就继续有效 |
| 每条断言都要哈希绑定 | 52 条回归、80 条命名断言、逐条依赖字节比对 | §4 只测黄金路径和本次改动影响到的路径 |
| 自己给自己加限制 | 分角预算账本、UI 租约、额度守卫、每次付费调用等人确认、120 秒监督窗口 | §6 一次性预授权预算；明确禁止自创流程 |
| 环境阻塞时原地等待 | Windows RDP 二次验证、云机磁盘满、下载慢 | §2 常驻测试环境；阻塞超过 30 分钟就升级给人 |
| 未知 = 阻断 | 任何没测到的子断言都写成 blocker | §7 只有 S1 阻断发版 |
| 线上数据不看 | 1.5.0 的失败事件没有错误码，1.5.5 的回归是上线后才从数据里发现的 | §8 线上数据才是最终验收，上线 2 小时和 24 小时各看一次 |

## 1. 角色与时间盒

| 角色 | 职责 | 可以是 |
|---|---|---|
| 发布负责人 | 冻结候选、判定级别、给出 GO / NO-GO、执行发版 | 维护者或主 agent |
| 验收执行人（Mac / Windows 各一） | 在安装包上按 §4 打勾、截图 | 维护者、测试者或 agent |
| 负责人（owner） | 授权发版、预算、豁免 | 只能是维护者本人 |

**时间盒：**

| 版本类型 | 从冻结到 Pre-release | 观察期 | 单平台人工验收上限 |
|---|---|---|---|
| 热修（S1） | ≤ 4 小时 | 2 小时 | 45 分钟 |
| 周版 | ≤ 1 个工作日 | 24 小时 | 90 分钟 |

超出时间盒，发布负责人必须二选一：(a) 按已有结果发，没测的项列进 Known Issues；(b) 推迟到下一版。不允许"再延长一点"。

## 2. 常驻测试环境与素材（一次性准备，每版复用）

**环境：**
- **Windows**：腾讯云 Windows Server x64 一台，做一个快照"干净 + 已装 v上个正式版"。RDP 登录由维护者保持会话，二次验证每周最多做一次。另外留一台 Windows 实机（自己或固定测试者），每个周版至少跑一次黄金路径。
- **macOS**：本机 Apple Silicon；独立的测试数据目录 `~/AutoClipQA/profile`，用环境变量隔离，不碰日常数据。
- 两端都预先放好**测试专用的模型配置**：一个分析模型、一个视觉模型（例如百炼 qwen3-vl-flash）、一个云 ASR，key 只存在测试 profile 里。

**固定素材库**（`~/AutoClipQA/assets`，不进仓库）：

| ID | 素材 | 用途 |
|---|---|---|
| A1 | 3 分钟中文访谈 + 配套 SRT | 有字幕主路径 |
| A2 | 3 分钟中文口播，无字幕 | 转写主路径 |
| A3 | 2 分钟英文播客 | 英文包装、平台文案 |
| A4 | 45 秒游戏录屏，无口播 | 视觉路径 |
| A5 | 一条 B 站短视频链接 + 一条 YouTube 短视频链接 | 链接导入 |

素材固定以后，每次结果才能互相对比；每版的付费调用也基本可预测（约 ¥3–5）。

## 3. 冻结规则（防止边测边修）

1. **冻结**：打候选构建时记下 commit。之后只有 S1 可以改代码。
2. **重建上限**：每个版本**最多重建 2 次**。第 3 次发现问题时，S1 走热修、发下一个补丁号；S2/S3 进下一版。
3. **攒批**：验收中发现的多个问题先全部记下，一次性修完再重建，不要发现一个修一个。
4. **结果复用**：重建后跑 `git diff <上次候选> <新候选> -- backend frontend/src src-tauri`。没有改到的模块，上次的勾选结果直接沿用；改到的模块，只重测 §4.3 对应的项。**不写承接证明**。

## 4. 验收内容

### 4.1 自动层（CI 自动跑，不需要人工）

Desktop Build 全绿即为通过：源码质量门、后端/前端测试、Windows IOCP/媒体回归、三平台真实 SenseVoice/Whisper 转写、Windows 覆盖安装冒烟。**CI 红 = 不进入人工验收**，先修。

每个 bug 修复**必须**带一条能在 CI 里跑的回归测试，测出修复前失败、修复后通过。人工验收只覆盖 CI 测不到的部分：真实 UI、真实模型、真实网络、安装包运行时。

> 已知缺口：安装包冒烟（`verify_windows_install.py`、`installed_video_acceptance.py`）目前走的是旧的 `/projects/upload` 流水线，没有覆盖首页的 `/studio/import` 一键出片。在改成走 Studio 之前，G3 必须人工执行。

### 4.2 黄金路径（每个版本、两个平台都要跑，每端约 30–45 分钟）

在**最终安装包**上按顺序做，每项打勾并截一张图：

| # | 步骤 | 通过标准 |
|---|---|---|
| G1 | 覆盖安装到"上个正式版"快照上，启动 | 窗口打开；设置里原有的 key 和项目都还在；没有一直 Loading |
| G2 | 设置页：改一次分析模型，点测试连接，保存，重启应用 | 测试连接成功；重启后配置保持；保存后不报错 |
| G3 | 导入 A1（带 SRT），一键出片 | 进度会走；成片能预览；字幕和画面对得上 |
| G4 | 导入 A2（无字幕），用已就绪的转写出片 | 转写完成并出片；如果转写没就绪，提示要明确告诉用户下一步做什么 |
| G5 | 导入 A5 的其中一条链接 | 下载进度会走，最后出片 |
| G6 | 任选一条成片：保存到本地、打开 ZIP、播放首/中/尾 | 文件能播放，有声音；ZIP 能打开，中文文件名正常 |
| G7 | 断网或填错 key，再触发一次出片 | 在 1 分钟内失败，提示可以理解；改回正确配置后重试能成功 |

Windows 和 macOS 都要跑 G1–G7。不需要另外做"干净安装"：G1 的快照每季度刷新一次，干净安装只在安装器有改动时补测。

### 4.3 改动影响项（只在本版改到时才跑）

按本版 diff 涉及的路径，挑出对应的项追加测试：

| 改动涉及 | 追加测试 |
|---|---|
| `services/studio/intelligence.py`、`planning.py`、视觉设置 | A4 自动模式出片；关掉视觉后 A1 仍能出片 |
| 转写（`whisper*`、`sensevoice*`、`cloud_transcription`） | 用改到的那条转写路线跑 A2 |
| 下载器、`youtube`、`bilibili` | A5 两条链接都跑 |
| `ai_model_settings`、设置页、迁移 | 从 1.4 / 上个正式版升级后打开设置；填错 key 的提示 |
| `store.py`、任务状态、`jobs.py` | 出片中途关掉应用再打开：任务不能卡在进行中，可以重试 |
| 打包、Tauri、运行时、CRT | Windows 干净快照安装一次 |
| 统计 / 隐私 | 关掉统计后重启，在 PostHog 里确认没有新事件；开着时确认 `studio_generation_finished` 入库了 |
| 包装、封面、字幕样式 | 把 A1、A3 的成片看完一遍 |

## 5. 证据（每个平台一页）

每个平台填一份 `docs/releases/vX.Y.Z/<platform>.md`：

```markdown
# vX.Y.Z · windows-x64
- 包：AutoClip Desktop_X.Y.Z_x64-setup.exe  SHA256: …
- commit: …   构建: Actions run …
- 环境：Windows Server 2025 x64 云机 / Win11 实机；测试 profile
- 执行人 / 时间：…

| 项 | 结果 | 备注 / 截图 |
|---|---|---|
| G1 | ✅ | g1.png |
| … | | |
| 4.3 视觉 A4 | ✅ | |

费用：约 ¥x（模型 / 次数）
发现的问题：#123（S2，已知问题）
```

截图和原始日志只保存在本地，仓库里只放这一页。不要为每条断言单独写 JSON、算哈希或写依赖证明。

这页结果转成 Internal / Release Acceptance 的 manifest：执行过的项填 `passed`；按 §7 决定不测的项填 `waived` 并写明理由（见 TESTING_ACCEPTANCE「负责人豁免」）。

## 6. 预算与授权（一次给足）

- 每个版本开始时，负责人一次性授权：**付费模型 ≤ ¥10**、打 tag、Pre-release、观察期结束后 Promote。执行时不再逐次确认。
- 超出预算、要联系外部测试者、要 halt 线上版本时，才再次请示。
- **agent 不得自行增加流程限制**，包括私人账本、UI 租约、额度守卫、监督窗口等。确实需要防护时，先写进本文并经负责人同意。
- agent 每 30 分钟用 3 行汇报：完成了什么、卡在哪、下一步。同一个环境问题卡住超过 30 分钟，停下来交给人，不要写工具绕过去。

## 7. 问题分级与 GO / NO-GO

| 级别 | 定义 | 对发版的影响 |
|---|---|---|
| S1 | 装不上、打不开、升级丢数据；黄金路径 G1–G6 中任一项在两端或 Windows 上必现失败；比上个正式版明显更差 | **阻断**。修复后只重测受影响的项 |
| S2 | 某个功能在特定条件下失败，有绕过办法；只影响非黄金路径 | 不阻断。写进 Release 正文的 Known Issues，排进下一版 |
| S3 | 体验、文案、边界情况 | 不阻断，进 backlog |

**GO 的条件**：CI 全绿；两个平台 G1–G7 没有 S1；本版的 4.3 追加项没有 S1。没跑到的项由发布负责人判断级别；判断不出来，默认按 S2 处理并写进 Known Issues。**未知不等于阻断。**

## 8. 线上观察（真正的验收）

Pre-release 之后、Promote 之后，各看一次（2 小时和 24 小时），每次 15 分钟，看三样：

1. **出片成功率**（PostHog）：`studio_generation_finished` 中 `material_origin=user` 的设备级 completed / (completed + failed)，按版本拆，和上个正式版对比。
2. **失败码分布**：同一事件的 `error_code` 前 5 名，有没有新出现的错误码，或者某个码的占比突然升高。
3. **Sentry**：`release:autoclip-backend@X.Y.Z` 下新出现、影响 ≥ 3 台设备的 issue。

**halt 条件**（满足任一条就执行 Promote / Halt Release 的 halt，退回上一个好版本，再往前修）：
- 样本 ≥ 20 台设备时，出片成功率比上个正式版低 10 个百分点以上；
- 出现一个新的、和本版改动相关、影响 ≥ 5 台设备的失败码或 Sentry issue；
- 出现安装或升级失败的 S1 反馈。

## 9. 一次发版的流程（照抄执行）

```text
T0       冻结 commit；bump_version；push 候选分支；触发 Desktop Build（约 30 分钟）
T0+0.5h  CI 绿 → 两端各装最终包，跑 G1–G7 和 4.3（并行，各 ≤45/90 分钟）
T0+2h    汇总两页证据 → GO/NO-GO
         GO：生成 manifest → Internal Acceptance → 打 tag → Pre-release（约 40 分钟）
T0+3h    Pre-release 上用 G3 做一次冒烟（10 分钟）
T0+5h    热修：观察 2 小时后看 §8 三样 → Release Acceptance → Promote
         周版：观察 24 小时
发布后   更新 #96 和 HANDOFF；回复并关闭对应 issue；2 小时 / 24 小时各看一次线上数据
```

## 10. 复盘（每版 5 分钟）

发版后在 `docs/releases/vX.Y.Z/` 里补三行：
- 实际用时 / 重建次数 / 费用；
- 线上发现、但验收漏掉的问题（如果有），以及要加进 4.3 表或 CI 的那一条；
- 下次可以删掉的步骤。

# AutoClip 数据需求：项目负责人和增长负责人视角

日期：2026-09-29。状态：业务需求草案，供确定范围；不是埋点实施方案，也没有变更当前路线图。

## 1. 数据要支持什么目标

依据目前讨论，AutoClip 希望成为持续帮助用户、有社区影响力、能够获得持续赞助的开源 AI 高光剪辑项目。近期服务重点是已有长视频到短视频的真实使用需求；游戏高光可以作为场景，游戏买量闭环暂不作为主线。

负责人需要判断三件事：

1. **价值是否成立：** 有多少人持续用它完成实际工作，结果是否达到使用要求。
2. **增长是否健康：** 哪些渠道和场景带来了真正用起来的人，新增关注能否转化为持续使用与传播。
3. **项目能否持续：** 有限维护时间是否花在有效改进上，社区和赞助能否提供持续支持。

数据的交付标准是能够指导“下周优先做什么、暂停什么、继续投入什么”。没有对应决策的数据，默认不进入第一期采集范围。

## 2. 两类负责人的核心问题

| 角色 | 每周要做的决定 | 必须看到的证据 |
|---|---|---|
| 项目负责人 | 修稳定性、改善引导、提高质量、增加能力，哪个优先 | 受影响范围、首次成功损失、用户认可程度、修复后变化、预计维护投入 |
| 项目负责人 | 优先服务什么场景 | 场景需求、首次成功、再次使用、输出质量、支持成本，不能只看谁反馈最积极 |
| 项目负责人 | 当前版本是否值得继续推广 | 版本覆盖、核心流程成功与未知结果、新问题、真实成片验收 |
| 项目负责人 | 哪些社区工作值得投入 | 有效反馈、贡献者首次贡献、持续贡献、维护响应与积压 |
| 增长负责人 | 去哪里发布、讲什么、用什么案例 | 渠道带来的有效尝试和首次出片、用户目的、传播素材表现、投入时间 |
| 增长负责人 | 流量来了之后先改善哪一步 | 首次访问到首次交付的可观测转化、流失原因、不同平台差异 |
| 增长负责人 | 哪些使用者愿意推荐，为什么 | 持续使用、主动推荐反馈、获准公开的实际案例 |
| 增长负责人 | 如何证明赞助价值且不损害用户体验 | 可核实的展示/点击、Provider 可用性、成功出片、合作收入与支持成本 |

同一个人可以兼任两个角色，但不把“传播表现好”当成“产品效果好”，也不以个别失败掩盖全部用户价值。

## 3. 负责人首页：先只放六组数

**核心结果指标：每周成功出片设备数，拆成首次成功和已有成功经历的设备。** 当前没有账户体系，统一称“可观测设备”，不包装成精确用户人数；采集关闭、数据未送达和多设备使用都形成边界。

成功出片在第一阶段定义为：使用非示例素材，产生有效视频，并得到该运行端能够确认的交付证据。桌面保存成功可作为证据；浏览器下载点击不够，浏览器确认交付暂缺时单列“成功生成/交付未知”。主指标先按运行端分列，不把证据强弱不同的数据加总成一个转化率。

| 首页信息 | 为什么需要 | 必须一起显示 |
|---|---|---|
| 本周成功出片设备，首次/已有成功经历拆分 | 是否真的帮助更多人完成工作 | 平台、数据覆盖范围、与过去完整周比较 |
| 新设备 7 日首次出片率 | 首次使用体验是否改善 | 成熟 cohort 的分子/分母、未知结果数、版本 |
| 首次成功后 28 日再次出片率 | 是否存在持续价值 | 满 28 日样本量、不同制作任务、场景；7 日指标作早期观察 |
| 本周阻止首次成功的前三类问题 | 下周优先修什么 | 受影响设备/执行数量、失败阶段、原因证据、未知原因 |
| 用户认可程度与质量反馈 | 出片是否达到使用要求 | 可直接用/需修改/不能用的反馈分布、回复率、样本来源 |
| 有效增长来源 | 下周继续在哪里投入 | 各渠道可归因首次成功数、归因覆盖、内容与时间投入 |

首页同时放一条“数据健康”状态：采集契约覆盖、终态未知占比、数据更新时间。数据异常时暂停解释业务涨跌。Star、版本下载量和曝光量放在增长页，不能取代上述结果。

## 4. 需求清单：问题 → 数据 → 获取方式 → 决策

### A. 谁需要我们，拿来做什么

**决策：优先服务哪类使用场景，展示什么案例，文案怎么写。**

- 需要知道：用途（访谈/播客、知识讲解、直播、游戏录屏、其他）、原先制作方式、使用频率、最希望省掉的工作、主要障碍。
- 数据：按场景的尝试设备、首次成功、再次出片、质量反馈、支持问题；样本量不足时只呈现原始数量与访谈结论。
- 如何获得：首次成功后提供一次可跳过的用途选择；结合自愿访谈和反馈标签。第一次启动尽量不增加填表负担。不分析视频正文来推断用户身份或职业。
- 补充方法：首轮邀请少量成功、失败和中途放弃的用户，分别覆盖主要平台。联系和访谈需在后续工作中取得授权，本需求阶段不发送邀请。
- 如何行动：某场景成功、复用和口碑都好，优先做相应预设与案例；需求强但失败多，先修可用性；只有少数高声量反馈时，不立即改变主线。

### B. 从哪里知道我们，为什么愿意尝试

**决策：渠道、教程、演示视频和发布节奏如何分配。**

- 需要知道：渠道与具体传播内容带来的访问、下载意图、可确认的首次启动、首次成功与再次使用；每条内容投入多少时间和现金。
- 如何获得：官网受控 campaign/source/content 标记与下载点击；仓库、发布渠道和发行资产提供的聚合数据；人工维护一张“内容发布时间—渠道—主题—链接—投入”台账。
- 安装到激活归因：如已有可信的安装来源传递能力，按明确规则关联；否则首次使用中提供可跳过的“从哪里知道我们”选择，并保留 unknown。直接从 GitHub 下载的来源链路可能断开，不强行拼接。
- 归因口径：第一期优先固定“已记录的首次来源”，来源方式分为链接标记/用户自报/未知。活动前后涨幅仅为相关性观察，不宣称全部增量由活动导致。
- 如何行动：高曝光低尝试，检查定位与案例；尝试多而成功少，检查渠道人群匹配和首次体验；带来复用的渠道优先持续投入。
- 限制：下载次数不是安装人数；官网下载点击不是实际下载完成；仓库访客、下载和匿名设备不能直接当成同一批人相除。无法贯通时展示分段漏斗。

### C. 第一次使用具体卡在哪里

**决策：配置、导入、理解、制作、保存，哪一步最值得改善。**

需还原的业务旅程：看到项目 → 尝试获取 → 打开可用界面 → 准备好所需能力 → 导入真实素材 → 获得可用候选/方案 → 制作 → 生成视频 → 确认交付。

这是一组可选路径，不要求人人经过同一套模型配置或确认页面；本地模型、已有配置、示例体验等单独标识。

- 数据：每步进入、成功、失败、取消、仍进行、未知；首次与重试；等待时长和操作时长；首次启动/导入到首次交付时长。
- 如何获得：应用内行为与执行结果摘要共同记录；平台、版本、入口、素材来源类型和时长区间作为受控维度。启动之前的安装阻断用下载后可选反馈、安装说明反馈和人工试装补充，应用内埋点无法观察完全打不开的安装包。
- 原因补充：对未完成行为只能说“未观察到下一步”；用户主动报告没时间、没 Key、太慢、不理解或不满意时，才记为对应原因。
- 如何行动：按影响的可观测新设备数量、阻断程度、证据可信度和解决工作量排序；不按错误日志条数排名。
- 示例流程：记录示例完成及随后是否尝试真实素材。示例成功衡量引导效果，不计真实首次出片。

### D. 成片是否有用，是否节省工作

**决策：提高选段、字幕、构图、声音还是动效，下一项质量工作做什么。**

三层证据分别保留：

| 层次 | 数据 | 获取方式与解释 |
|---|---|---|
| 技术完成 | 有效视频、音视频完整、成功交付 | 自动校验和交付结果；不代表内容好 |
| 实际可用 | 可直接发布/小改后可用/需要大改/不可用；原因分类 | 在交付后适度抽样询问，可跳过；展示回复率，不能外推未回复者 |
| 最终价值 | 是否实际使用或发布、节省多少时间、是否愿意再次使用/推荐 | 自愿回访、用户自行提供的案例；时间节省采用区间自报，注明估算 |

需要分解的质量问题：精彩片段是否找对、上下文是否完整、字幕是否准确可读、竖屏是否裁错主体、声音是否清楚、节奏是否拖沓、视觉风格是否适合内容。

如何获得可比较证据：建立少量有使用许可的固定素材和评分规则，在相同素材/配置下比较版本；以人工盲评为主，记录评审者和分歧。用户侧仅采集受控反馈类别，不默认上传成片或字幕。修改次数、导出次数可以作线索，但不能直接当满意度——编辑可能是主动创作。

决策规则：只有当实际失败/反馈/基准共同指向某个质量问题，才提高相应优先级。外部动效演示可以提供灵感，但不能替代我们的用户需求证据。

### E. 成功后会不会再次使用

**决策：持续价值是否成立，下一步应扩大获客还是改善产品。**

- 数据：首次成功 cohort 在 7/28 日内完成另一次不同制作任务的比例；每周成功设备中新/老构成；不同场景的制作频率。
- 如何获得：匿名设备下的成功交付记录与本地任务关联。重新下载、同一任务重复渲染不能算再次使用；新制作任务作为第一期可验证代理，不声称识别了全新的素材内容。
- 分母：以第一次真实交付为起点，仅纳入观察窗口已结束的 cohort。最后一周的用户不能与成熟的老 cohort 直接比较。
- 如何解释：长视频创作者可能按周或按月工作，不把每日打开当目标。打开但没出片是辅助信号；低频场景需要结合预期使用频率和回访。
- 如何行动：首次成功增加但再次出片偏弱时，先访谈结果质量、重复工作与需求频率；不要立即设计推送或催活。

### F. 新版本有没有改善，项目能否维护得住

**决策：继续推广、修复、延后新功能，以及分配维护时间。**

- 数据：版本/平台覆盖，制作任务一次成功率、重试挽回、未知终态，p50/p90 等待时间；阻断问题积压、重复反馈、响应时间和维护小时数。
- 获取：业务执行结果提供分母，Sentry 提供故障位置和分类，Issues/反馈提供用户影响，发布台账提供版本与修改目标；每周粗略登记维护时间即可。
- 版本比较：同时看用户构成、场景、素材时长和 Provider 类别变化。新版本早期用户不同，简单前后对比只能提供线索；固定素材回归与实际案例补充验证。
- 规则：质量指标不以静默、超时未上报为成功；无法分辨的终态展示未知。故障数量下降也可能是使用量下降，必须结合成功任务与可观测覆盖。
- 行动：稳定性足够、真实首次成功改善后扩大传播；支持成本过高的能力先收敛或改善默认设置。

### G. 社区影响力有没有变成持续参与

**决策：如何投入文档、贡献者支持和内容传播。**

- 关注层：新增 Star、仓库访问、外部提及、教程和引用；分别展示，不合成虚构“影响力总分”。
- 参与层：可复现反馈、外部贡献者首次贡献、首次响应时间、PR 等待时间、持续贡献者、获准公开的真实案例。
- 获取：GitHub 可提供的仓库/Issue/PR 数据，人工维护外部教程与案例清单。按定期快照留存趋势，具体接口可用性与保留窗口在实施时确认。
- 口径：外部贡献排除维护者和机器人；修复、文档、翻译都可算贡献。合并数量不是审查目标，关闭原因和等待时间用于发现协作障碍。
- 行动：关注多参与少时改善贡献入口；投稿多但积压严重时先改善评审负担；案例多则优先整理并经许可展示。
- 边界：GitHub 贡献身份与应用匿名设备保持分离，不尝试识别某个 Star 用户在应用中做了什么。

### H. 赞助是否有效且可持续

**决策：接受什么合作、如何续约、投入多少集成与支持。**

- 项目侧：实际收到的现金、可实际使用的资源额度、有效期、合作续期、集成和维护小时、直接支出。现金与额度分列，承诺金额与到账分列。
- 合作方侧：可确认的展示范围、应用内/官网出站点击、配置保存、连接成功、选用该 Provider 的成功出片；注册、付费、结算仅在合作方有可信回传时单列。
- 用户侧：赞助 Provider 的配置完成、调用可用性、任务成功、问题反馈。不能因为有赞助就把点击或默认选中当采用。
- 获取：公开产品数据仅聚合到渠道与受控 Provider；合同、联系方式、收入与结算台账保存在私有位置；合作方报表注明来源和归因规则。
- 行动：有用户价值且维护成本合理，才继续集成和续约；仅有曝光价值的合作按展示合作评价。不得向合作方提供用户素材、密钥、联系方式或设备级行为记录。

## 5. 获取数据的责任边界

| 数据来源 | 负责回答 | 不负责回答 | 初期维护方式 |
|---|---|---|---|
| 应用匿名统计/业务结果 | 使用步骤、成功交付、复用、可观测路径耗时 | 自然人身份、未启用统计人群、实际满意度 | 自动采集和固定报表 |
| Sentry | 受控工程异常与定位 | 业务成功率和真实用户数 | 按影响人工分诊 |
| 官网/渠道/仓库聚合数据 | 触达、兴趣、下载意图、社区关注 | 跨平台完整用户旅程 | 每周汇总，必要时自动化 |
| 自愿反馈与访谈 | 目的、放弃原因、可用性、时间节省 | 全量总体比例 | 轻量标签和案例笔记 |
| 固定样本评测 | 同素材下版本质量差异 | 所有真实用户的质量 | 每个重要版本重复评测 |
| 私有运营台账 | 推广投入、赞助收入、维护成本 | 应用内精确行为 | 一张表起步 |

第一期不新增数据仓库或强制账号。现有 PostHog/Sentry 和简单台账是否足够，由上述需求验收决定；实施方案随后再定。

## 6. 所有指标的统一口径要求

1. 明确统计对象：设备、制作任务、执行尝试、成片、反馈、贡献者分别统计，不相互替代。
2. 明确时间：运营周按 Asia/Shanghai 周一至周日；用户窗口按实际起点计算 7×24 或 28×24 小时。当前未结束周单列。
3. 明确样本：排除开发、验收、示例和可明确识别的内部测试；未知来源或未知结果保留，不静默剔除以美化结果。
4. 明确成功证据：接口受理、处理完成、生成视频、保存、实际使用逐级区分。多目标部分成功单列，任务全成功与至少交付一条不是同一指标。
5. 明确身份边界：匿名设备不等于自然人；清理存储/换设备可能重复计入。第一期不为去重引入指纹识别。
6. 明确数据成熟度：窗口未结束的 cohort 不做最终转化结论；延迟补报有发生时间与观察时间，报告标注截至时间。
7. 明确可信度：每个比率显示分子/分母；小样本仅作方向线索，不设置未经验证的行业目标，不宣称因果。
8. 明确归因边界：可直接关联、用户自报、聚合趋势三类证据分开。source=unknown 不是数据清洗错误。
9. 明确观察限制：无法测得全部关闭统计的用户，也不能从已观察数据推算精确总体覆盖率；“终态覆盖率”仅针对已登记可观测任务。
10. 明确信息范围：不默认收集视频/字幕/文件名/路径/接口地址/Key/自由文本；反馈为独立主动提交。历史缺字段不能靠推测回填。

## 7. 第一阶段交付范围

### 必须先有

- 一份指标字典：负责人、用途、统计对象、公式、窗口、维度、来源、排除项、可信度限制。
- 一条真实素材到确认交付的可验证业务链路，以及失败、取消、未知和重试口径。
- 六组负责人首页数据；暂时无法可信计算的显示“待建设/未知”，不造历史数。
- 一张获客内容与渠道投入台账；渠道归因先接受不完整。
- 一套简短的质量反馈问题与少量固定素材评审；先验证问题能否指导产品决定。
- 一份每周复盘：结果变化、最大阻碍、用户证据、下周一项重点改进及验证指标。

### 基线稳定后再增加

- 自动化渠道到激活归因、赞助方转化回传、贡献者持续参与趋势、CLI/MCP 使用分析。
- 更细的功能采用与质量细分。只有准备据此做决策时才增加。
- 实验平台或 A/B 测试，待样本量和可比较条件满足后再讨论。

### 当前不作为目标

- 把 DAU、点击量、事件数量、Star 单独设为团队成功标准。
- 用户付费、订阅收入、广告 ROAS 等尚不符合当前主线的经营体系。
- 全量行为录屏、跨站设备识别、为了分析强制注册。
- 用 LLM 给全部成片打总分替代实际用户评价。

## 8. 需求验收：负责人应能回答这些问题

1. 上周有多少可观测设备真正拿到了非示例成片？多少第一次成功？哪些平台还无法确认？
2. 新设备 7 日内首次成功的比例是多少？具体分母是谁？失去观测的有多少？
3. 首次成功最主要的阻碍是什么？依据是执行记录、用户反馈还是推断？
4. 用户回来完成了新的制作任务吗？是否已经有足够成熟的观察窗口？
5. 用户最不满意的质量问题是什么？有多少人回答、固定样本是否也能复现？
6. 上周发的教程/演示带来了什么？哪些只知道点击，哪些能看到首次成功？
7. 新版本是否改善了目标问题？有没有平台回退或新的未知数据？
8. 社区贡献和赞助是否减少维护压力、支持长期发展？哪些投入反而增加负担？

任一答案都应能回到定义和数据来源。无法回答时应明确缺的是采集、关联、样本、时间窗口还是人工研究，不继续用一个新事件名称掩盖需求缺口。

## 9. 建议的每周复盘模板

```text
统计周 / 数据截至时间 / 覆盖平台与版本 / 数据异常

价值：成功出片设备，首次与已有成功经历拆分；用户可用性反馈
激活：最新成熟 cohort 的 7 日首次成功率；前三类阻碍
复用：成熟 cohort 的 7/28 日再次出片；场景差异
增长：各渠道可确认贡献、未知归因、推广投入
项目：版本问题、社区协作、维护时间；赞助月度补充

本周判断：发生了什么；证据强弱；还有什么解释
下周决定：只选一项主要改进；预期改变哪个指标；如何验证
```

本稿先确定业务问题和证据标准。事件名称、ID 设计、SQL、具体图表和代码变更由下一步技术方案承接，不作为本轮需求梳理的替代。

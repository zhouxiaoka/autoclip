## 已实现的首版

桌面版「设置 → 应用 → OBS Studio」提供同机连接、密码清除和自动出片。新安装默认关闭自动出片。启用时列出本机配置里可能接收音频、字幕和抽帧的模型及服务主机（兼容官方 OpenAI、Gemini 及 OpenAI 兼容服务商）。默认每场最多 50 次请求，可设为 1–500 次，次数上限不对应固定金额。连接可使用兼容的 5.x 服务，自动出片要求 5.5+，以便检测录像分卷。自动任务沿用 Studio 分析配置，使用 45 秒目标和原画幅，跳过自动 AI 封面；手动选场则统一回到首页由用户自选发布平台与规格。隐私边界裁剪在起止偏移 ≤1 秒时跳过，超出时优先按内向关键帧执行秒级 `-c copy` 无损流拷贝，仅在关键帧跨度过大时回退重编码。

场次关联只在一次连续连接内有效。握手阶段缓冲竞态事件，修改自动化开关或预算不再断开进行中的 WebSocket 连接；授权变更后自动降级为可手动选择的回放。双终态落库后可重启继续验文件，开播时已经在进行或跨断线的场次由用户手动导入。SQLite 事务预留项目和调用，按签名复用已返回结果。领取后崩溃或模型已发送但结果未知时，停止自动重试；确定性 4xx 鉴权/限流错误给出清晰状态与文案。最近一次导入支持打开项目。模型或转写预检失败时显示单独的修复提示。下文中按金额设预算、多文件归属和双平台安装包验收是扩展或验收事项。

## 实测记录

- OBS Studio 30.2.3、内置 obs-websocket 5.5.2 在隔离的 Linux arm64 环境向回环 RTMP 推流，桌面后端在 macOS arm64 源码环境运行。只录屏时为 0 个项目、0 次模型调用。下播后继续录像时仍为 0。MKV 写完后自动创建 1 个项目。Qwen 4 Max 视觉路线实际发出 3 次请求，生成 6 条可解码的 MP4。此联调使用虚拟屏幕上的公开游戏素材。
- 默认自动路由另用两份完整回放验证。Northernlion 的解说样本产生 5 条视觉候选，均未覆盖预先登记的第一名结算。Blue Scuti 的画面样本产生 2 条，首选从 38:30.15 开始，保留主播反应，开头棋盘已冻结，缺少最后操作。该轮共 19 次 Qwen 请求，按实验记录的单价估算约 0.63 元。两场的预设路线与选段标准见文末。导出成功只证明有可审素材，不能当作高光命中率。
- 本机开发联调与发布验收分开记录。macOS 和 Windows 的最终安装包、系统凭据、休眠和重启恢复仍需按发布清单验证。公开仓库仅保留汇总，不包含录像、字幕、私有路径、模型密钥或逐请求内容。

## 首次连接和每次下播

设置页提供「连接 OBS」与「下播后自动出片」两个控件。首版支持同一台电脑上的 OBS Studio 28+ 内置 WebSocket 5.x、桌面版 AutoClip 和本地录像。用户在 OBS 的「工具 → WebSocket 服务器设置」开启服务，输入端口（默认 4455）和密码。连接成功显示 OBS 版本、连接状态和是否正在录像。凭据存系统钥匙串或 Windows 凭据存储，后端只取引用，前端不持久化密码。监听组件随桌面后端启动，退到后台可继续；完全退出期间错过的场次提示手动导入。连接和断开均不改变 OBS 的推流、录像、场景或平台账号。

自动出片默认关闭。开启前按实际模型配置列出接收方、可能发送的数据（云转写的音频、文本模型的字幕、视觉模型的抽帧、可选封面图片）、可能的按量费用与预计范围或无法估算的原因。首版建议自动项目默认关闭云封面、仅生成一个原画幅版本。记录同意的用途、服务商、模型、费用上限、版本和时间；预算可按用户设定或明确的产品默认值落实。预算无法约束时先待确认。服务商、外发范围或预算扩大时重新同意。关闭自动出片使待派发任务与尚未发出的调用停止，已返回的结果保留。从下一场完整可观察的直播起生效。结果在项目列表中可预览、修剪或丢弃，默认待审核。

## 何时有资格建项目

WebSocket 完成 Hello → Identify → Identified 后订阅 Outputs 事件，调用 GetVersion、GetStreamStatus 和 GetRecordStatus 校准当前状态。事件应在握手后立即排队，状态查询与事件共用串行处理，启动期间有冲突就等待下一次可确认的开始。协议给出推流状态、录像状态及停止落盘路径，没有跨重连的永久直播 ID。AutoClip 为连续观察到的开播生成本机场次 ID，并持久化。用实际观察到的推流与录像区间重叠建立关系，支持先录后播、先播后录，以及先停录后下播。分别记录录像暂停、平台推流重连与 WebSocket 断开。[OBS 远程控制指南](https://obsproject.com/kb/remote-control-guide) · [OBS WebSocket 5.x 输出事件与请求](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#outputs-events)

| 观察到的情况 | 系统行为 |
|---|---|
| 完整开播后收到 StreamStateChanged 的 OBS_WEBSOCKET_OUTPUT_STOPPED，匹配的录像仍在录或暂停 | 显示「已下播，等待 OBS 保存录像」，不派发 |
| 匹配的录像先 STOPPED，并有 outputPath，直播仍在进行 | 持久保存路径和匹配证据，继续等推流 STOPPED |
| 两者已终止，存在唯一归属且文件完整 | 执行文件检查和模型/同意预检，通过后原子建项目、排队 |
| 只有录屏、回放缓存、只有推流、录像完全在下播后才开始 | 跳过，可手动导入；不能根据目录中最新文件猜测 |
| STOPPING、RECONNECTING、RECONNECTED、录制暂停，或只有 outputActive=false 快照 | 保留观察状态；这些信号均不能独立证明下播并落盘 |
| WebSocket 断线、OBS 重启、应用重启 | 恢复已落库的双终态并继续验文件；缺关键转换的场次标为「归属待确认」。一次重连前后两个空闲快照不足以补齐事实 |
| 同一录像跨两场直播、分卷、同场多次启停录像 | 首版仅自动处理完整单文件且只属于一场的录像。已知多文件或歧义时显示原因并保留手动入口；不能只剪最后一卷 |
| 回调重复、进程并发或用户重连 | 返回已有场次/项目/任务和当前状态 |

保存 OBS 输出版本和分卷可观察性。RecordFileChanged 从 WebSocket 5.5 起可用于发现换卷，事件中的 newOutputPath 指刚开始写的新文件。对于无法可靠发现分卷的版本，只在能验证单文件条件时自动处理，否则要求确认。自动 remux 后以能证明来自本次录像的成品为准；原路径消失不能靠相近文件名补配。对于录播起止相差很大的文件，建议持久化直播与录像的重叠区间。只有能将该区间可靠映射到媒体时间轴（含暂停）时才自动剪取；映射不清时交给用户选择，避免把开播前或下播后的私人桌面送模型。

## 从落盘到现有 Studio

1. 单个桌面后端监听同机回环地址，校验握手、事件顺序并维护连接代次。断线指数退避，错误密码提示更新。WebSocket 客户端只读。前端订阅本地后端的进度，关闭设置窗口不影响已开始观察的场次。
2. 文件门槛要求本地授权录像目录下的普通文件、稳定的大小与修改时间、实际可打开读取、媒体有视频轨和有效时长，能解码首尾。短间隔稳定检查仅辅助判断；必须已有录像 STOPPED。对刚落盘、Windows 占用、磁盘满和 remux 中设置有限等待与可恢复状态。导入时经打开的文件句柄复制到私有临时位置，校验前后文件身份/大小，原子改名后交给 Studio。用户原录像保留。
3. 抽出本地文件导入服务，复用 backend/api/v1/studio.py 的预检和素材保存语义、studio/preflight.py、studio/jobs.py 的 inspect_project 与现有工作区。保留手动导入调用方。当前 /api/v1/studio/import 的每次 POST 都新建项目并启动检查；OBS 重放事件直接重调该接口会产生重复项目。SQLite 中保存场次、素材身份、project_id 及待派发记录，以实际数据库唯一约束覆盖并发。项目和待派发记录在同一事务提交，文件采用可恢复的 staging。worker 原子领取后使用稳定 run/attempt 标识，崩溃恢复读取已有状态。
4. 付费防重做到每个逻辑调用。以场次、素材版本、分析阶段、分块/帧批、参数版本为唯一键，发送前写入意图和预算预留。已成功直接读缓存。服务商明确支持幂等键时按其契约恢复。已发送但结果未知、服务商不能核对时标记「调用状态待确认」，冻结该步及预算；禁止超时后自动重发。原来的网络层自动重试也须服从该约束。项目去重本身覆盖不了供应商已计费而客户端崩溃的窗口。
5. 完成后在现有 Studio 项目显示实际候选、可播放成片和来源「OBS」。区分成功、部分完成、无高光、配置需处理及模型状态未知。将 source=obs 和有界原因码接入终态生产、查询与验收；不收集录像路径、口令、字幕、帧、直播标题。首次触发与重复回调分别计数，成片数取实际可播放产物。

## 游戏素材与长直播

当前 planning.resolve_route 会把时长超过 7,200 秒的素材导向字幕。intelligence.analyze 对可走视觉路线的完整素材最多粗采 60 帧，仅对排名第一的候选做最多 25 帧的复核。60 分钟样本粗采间隔约 60 秒，严格大于 120 分钟的无口播长直播即使有音轨，也不能据此承诺能自动找到高光。字幕有利于捕捉主播的铺垫与反应，但可能选中与画面无关的闲聊。

接入时要验证一个容易遗漏的组合：当前 recommend 在显式 goal=highlight 时跳过 AI 初筛，而 auto 分析要在初筛实际发生后才会选择视觉路线。不能把「高光」预设直接写死就假设游戏将走视觉。建议监听器沿用用户同意的分析方式，智能模式以 goal=auto 进入现有规划；把口播、游戏实况和选错路由列入真实回放验收。若要求某场强制视觉，应作为该项目的显式选择独立测试。

首版在待审核页显示实际路线和降级原因。对无可用语音且超出现有视觉上限的录像，保留素材并提示选择处理区间；不要无提示只剪前半小时。候选质量确有缺口时，再独立评估分窗粗筛、利用本地画面/声音变化提出候选、对多个候选加密复核的收益和模型费用。接入 OBS 只解决触发和归属，不能单独改善模型选段。

## 两场游戏回放对接入决策的影响

2026-11-18 在上述源码上经 Studio 本地导入实际运行。使用整场文件，原画幅、目标 45 秒，分别指定字幕或视觉分析；每场先从原片标记一个关键事件，时间码不传给模型。Qwen4-Max 的 15 条导出均有音视频轨且全文件解码通过。

| 回放 | 云端结果 | 首版要处理的问题 |
|---|---|---|
| Northernlion《Tetris 99》，60:44，解说多 | 字幕路线导出 9 条。首选覆盖 24:54–24:56 的第一名结算，但成片长 150.4 秒、跨到下一局。9 条都超过 45 秒，也选入高尔夫等闲聊 | 待审核卡提供原片定位和裁切。把目标时长、事件结束与下一局切换同时列为验收项；关注游戏术语误识别后被写进标题 |
| Blue Scuti 的 NES《俄罗斯方块》，42:03，以画面为主 | 视觉路线导出 6 条。首选截取 38:26.5–39:05.0，看到最后几次落块、棋盘冻结和主播反应。第二条再次选到冻结后的反应 | 跨候选对同一事件去重时计入因果关系，仅以片段时间重叠去重会漏掉这类重复 |

本地 Qwen2.5-VL-3B 量化对照中，解说导出 9 条，均未覆盖该次夺冠；视觉候选格式校验失败，未导出。此结果支持首版将模型生成的候选送入人工审核。两场同系列游戏均不足两小时，以下补测记录默认自动选路与真实 OBS 连接。其他游戏和两小时以上的直播仍待验证。[Northernlion 原始回放](https://www.youtube.com/watch?v=cM6DK5W9WnU) · [Blue Scuti 原始回放](https://www.youtube.com/watch?v=J9oVQ43j22g)
